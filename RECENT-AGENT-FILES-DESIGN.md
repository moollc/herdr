# Recent agent files: capability and design note

Date: 2026-10-24
Branch base: `514e5910ee8f2d9326b92dc068b683781a8e8d3d`

## Alternatives considered

1. Keep the 20-second workspace `mtime` scan, expand it to `~`, or scan common output folders. Rejected: it has no author provenance, is incomplete at its caps, and inclusion would depend on path/depth policy.
2. Infer ownership from a busy pane, current working directory, or a recent agent turn. Rejected: those signals cannot prove which process wrote a path.
3. Parse agent session transcript/rollout history. Rejected as the primary source: Herdr's Codex model probe reads rollouts for model/title data, while three sampled recent Codex rollouts exposed generic `exec` items and no normalized file-write event. Parsing command or tool payloads from those logs would also risk retaining or exposing private content.
4. Consume provider post-write hooks and retain only explicit paths plus event provenance. Chosen for direct writes. Use a bounded, durable Herdr state journal independent of workspace and file location.

## Evidence and capabilities found

- `src/recent_files.rs` originally scanned only `workspace.identity_cwd`, every 20 seconds, and ordered by filesystem modification time. It could not attribute a write.
- `src/integration/mod.rs` already registers Codex `PostToolUse` hooks; the shipped state hook used them only for turn state. The provider's Hooks documentation describes post-tool `tool_name`, `tool_input`, and `tool_response`, including tool calls named `apply_patch` and shell tools. The installed source also samples Codex rollout records through `src/agent_model.rs`, but not as a write event source.
- The companion provider's Hooks documentation defines command hooks receiving JSON on stdin, `afterFileEdit` with an absolute `file_path`, and `postToolUse` for successful tools. Its `Shell` payload has `tool_input.command`, `cwd`, and `tool_output` as JSON text containing `exitCode`; `postToolUseFailure` is a separate failure event. Herdr originally registered only lifecycle hooks.
- Before isolated probes, the actual local Codex hook inventory contained only `SessionStart` and `UserPromptSubmit`; the actual local Cursor inventory contained `beforeSubmitPrompt`, `preToolUse`, `sessionStart`, and `stop`. Three recent Codex rollout files were sampled by metadata only: records included `response_item`, `event_msg`, `turn_context`, and generic `exec`; no normalized file event was present in the sampled structure. Later live probes used only disposable project-level hook files and isolated CLI config/state directories.
- Herdr's established state root is `config::state_dir()` (`~/.local/state/herdr` or `herdr-dev` for development, with XDG override). The captured journal path is exposed only to child processes in a Herdr pane. No live Herdr/provider state is changed by this source-only branch.

## Capture boundary

- Codex `PreToolUse`/`PostToolUse` and Cursor `preToolUse`/`postToolUse` pair through the provider's `tool_use_id`. The helper accepts only explicit paths from supported write/edit/patch tools or recognized shell destinations. It fingerprints those exact files before and after the same provider tool event, then journals a path only when the file is observed to be newly created or changed. A string `tool_response`, JSON-looking stdout, `tool_output`, or status text is never used as success evidence. A failed tool that changed its named file may be recorded; a failed or successful no-change call and a pre-existing unchanged file are not recorded as writes. Cursor `afterFileEdit` remains an explicit-path fallback, though the isolated live runs did not emit that event.
- Pair state contains only a SHA-256-derived opaque tool event key, canonical candidate path, start time, and regular-file fingerprint (`device`, `inode`, mode, size, `mtime`, and `ctime`). It is capped at 64 events and 512 KiB, expires after 120 seconds, and is rewritten atomically under a lock. Missing IDs, unmatched posts, expired/evicted pre-events, and incomplete candidate lists produce pathless gaps rather than file claims. The journal is separately locked and atomically replaced. A process crash between observing a change and committing the journal can leave a stale pair that later surfaces as a gap.
- Codex Bash and Cursor Shell recognize explicit output destinations (redirection, `tee`, `touch`, `cp`, `mv`, and `install`). Relative paths resolve against the provider's absolute working directory; absolute paths outside cwd are supported. Shell parsing skips a command segment containing `cd`, a subshell, or a recognized wrapper because destination meaning or side effects cannot be proven. It recognizes `&>` and `&>>`; fd digits count only when attached to `>`, so `echo 2 > report.txt` remains a stdout destination while stderr-only redirects do not. Unsupported wrappers with a candidate destination create a pathless gap. Arbitrary script/build/program side effects remain outside coverage unless the command explicitly names a supported destination.
- Path canonicalization follows symlinked parent directories and rejects invalid or non-regular results at fingerprint time. A separate process can still change the same explicitly named path during the tool window; the paired fingerprints cannot distinguish that race from a change made by the agent. The helper does not scan directories, run or persist command text, or store file contents. Hook timestamps are receipt times, not filesystem write times.
- Repeated writes to one path deduplicate to the newest hook event. Event IDs include a path digest, so separate files in one provider generation remain distinct. A capped 500-record / 512 KiB journal persists across restart and marks loss of older history as partial. The activity journal and its atomic-update files cannot appear through directory scanning because the product no longer scans output directories; an explicit self-path event is ignored.
- Existing panel rendering, mouse mapping, and literal-argv default-app opener remain. Keyboard focus requires a visible viewport, and partial/corrupt journal state is surfaced. Rows show provider when space allows; the journal retains tool provenance.

## Validation evidence boundary

The hook tests replay provider-shaped Codex/Cursor events through the actual helper entrypoint and check creations, changes, no-change calls, failures, mismatched IDs, stale state, limits, parser boundaries, and journal behavior. They remain stand-in payloads, separate from the live captures. `HERDR_ENV`, `HERDR_PANE_ID`, and `HERDR_STATE_DIR` are required; agents outside a Herdr pane or launched before this integration update capture nothing. Codex CLI `0.163.0` emitted matching `PreToolUse` and `PostToolUse` `tool_use_id` strings for Bash and `apply_patch`; `tool_response` was a string without status metadata, and the helper journaled both changed candidate files. Cursor Agent `2026.10.22-27dcf5f` emitted paired `preToolUse`/`postToolUse` events for `Write` with `tool_input.file_path` and `tool_use_id`; it journaled the harmless direct-editor output. Its paired Shell event also journaled an absolute path outside the project cwd. The runs used isolated project hooks/configs, retained only event field types, hashed event IDs, safe test paths, helper journal deltas, and required Herdr child environment values; no prompt, command, file contents, raw payload, email, or session identifier was retained. No team configuration or production hook installation changed.
