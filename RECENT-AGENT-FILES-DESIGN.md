# Recent agent files: capability and design note

Date: 2026-10-24
Branch base: `514e5910ee8f2d9326b92dc068b683781a8e8d3d`

## Alternatives considered

1. Keep the 20-second workspace `mtime` scan, expand it to `~`, or scan common output folders. Rejected: it has no author provenance, is incomplete at its caps, and inclusion would depend on path/depth policy.
2. Infer ownership from a busy pane, current working directory, or a recent agent turn. Rejected: those signals cannot prove which process wrote a path.
3. Parse agent session transcript/rollout history. Rejected as the primary source: Herdr's Codex model probe reads rollouts for model/title data, while three sampled recent Codex rollouts exposed generic `exec` items and no normalized file-write event. Parsing command or tool payloads from those logs would also risk retaining or exposing private content.
4. Consume provider post-write hooks and retain only explicit paths plus event provenance. Chosen for direct writes. Use a bounded, durable Herdr state journal independent of workspace and file location.

## Evidence and capabilities found

- `src/recent_files.rs` originally scanned only `workspace.identity_cwd`, every 20 seconds, and ordered by filesystem modification time. It could not attribute a write.
- `src/integration/mod.rs` already registers Codex `PostToolUse` hooks; the shipped state hook used them only for turn state. OpenAI's [Hooks documentation](https://developers.openai.com/de-DE/docs/hooks) describes post-tool `tool_name`, `tool_input`, and `tool_response`, including tool calls named `apply_patch` and shell tools. The installed source also samples Codex rollout records through `src/agent_model.rs`, but not as a write event source.
- Cursor's [Hooks documentation](https://prod.cursor.com/docs/hooks) defines command hooks receiving JSON on stdin, `afterFileEdit` with an absolute `file_path`, and `postToolUse` for successful tools. Its `Shell` payload has `tool_input.command`, `cwd`, and `tool_output` as JSON text containing `exitCode`; `postToolUseFailure` is a separate failure event. Herdr originally registered only lifecycle hooks.
- The actual local Codex hook event inventory contained only `SessionStart` and `UserPromptSubmit`; the actual local Cursor inventory contained `beforeSubmitPrompt`, `preToolUse`, `sessionStart`, and `stop`. Three recent Codex rollout files were sampled by metadata only: records included `response_item`, `event_msg`, `turn_context`, and generic `exec`; no normalized file event was present in the sampled structure. No provider configuration was edited.
- Herdr's established state root is `config::state_dir()` (`~/.local/state/herdr` or `herdr-dev` for development, with XDG override). The captured journal path is exposed only to child processes in a Herdr pane. No live Herdr/provider state is changed by this source-only branch.

## Capture boundary

- Codex `PostToolUse` and Cursor `afterFileEdit` record paths from successful provider write/edit events, including outside-cwd paths, untracked files, and any extension. For Codex, the helper requires a parseable success result (`exit_code`/`exitCode` zero, `success: true`, or a success status); unknown responses are skipped and add a pathless partial-state marker. Cursor direct-edit events explicitly name the path.
- Codex shell capture and Cursor `postToolUse` matched to `Shell` recognize explicit output destinations (redirection, `tee`, `touch`, `cp`, `mv`, and `install`). Cursor requires JSON `tool_output.exitCode == 0` and resolves relative paths against payload `cwd`; Codex uses payload `cwd`, overridden by an absolute `tool_input.workdir` when supplied. Both support direct harmless outputs outside cwd. The helper does not run or persist command text and is not a shell interpreter.
- Shell parsing skips a command segment containing `cd`, a subshell, or a recognized command wrapper because relative-target meaning or side effects cannot be proven. It recognizes `&>` and `&>>`; digits count as an fd only when attached to `>`, so ordinary arguments such as `echo 2 > report.txt` remain supported. Unsupported contexts and unverified/failed relevant events add a pathless journal row, which the UI reports as partial. Unseen script/build/program side effects remain outside coverage unless the command explicitly names a supported destination.
- Repeated writes to one path deduplicate to the newest hook event. Event IDs include a path digest, so separate files in one provider generation remain distinct. A capped 500-record / 512 KiB journal persists across restart and marks loss of older history as partial. The activity journal and its atomic-update files cannot appear through directory scanning because the product no longer scans output directories; an explicit self-path event is ignored.
- Existing panel rendering, mouse mapping, and literal-argv default-app opener remain. Keyboard focus requires a visible viewport, and partial/corrupt journal state is surfaced. Rows show provider when space allows; the journal retains tool provenance.

## Validation evidence boundary

The hook tests replay small documented Codex/Cursor payloads into the actual capture helper and create harmless text/HTML fixture outputs. This proves the helper's supported workflow with mock/capture evidence; it is not a live Codex or Cursor session. Herdr pane environment variables (`HERDR_ENV`, `HERDR_PANE_ID`, and `HERDR_STATE_DIR`) are required; agents outside a Herdr pane and agents launched before the integration environment update capture nothing. Codex capture is limited to `PostToolUse` direct write/edit/patch/create tool names and the supported shell destination syntax; it does not observe MCP or arbitrary subprocess side effects. Hook timestamps are receipt times, not filesystem write times. The local Codex CLI was `0.163.0`. Current Cursor documentation defines `postToolUse`, but Cursor desktop and its build were not found on this Mac, so Cursor version and payload delivery are unverified. Current local configs lack the new hook registrations, and no live provider delivery has been tested; live delivery remains unproven until a reviewed integration is installed and exercised.
